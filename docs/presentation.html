Gap 1 — Detection

Standard confirmatory tests — eGFR, serum creatinine, UACR — require dedicated laboratory access and phlebotomy. This creates a barrier in community, primary-care, and low-resource settings where early screening is most needed.

Gap 2 — Patient Education

Even when a risk score is generated, patients receive no personalised guidance — no explanation of what their specific risk factors mean, what lifestyle changes to make, or when to seek follow-up. Generic advice is ignored.

Existing ML Models Fall Short
  • Almost all use eGFR or creatinine as input — not accessible for screening
  • Binary classification only — no KDIGO-aligned risk stratification
  • No patient-facing education layer built in

Why NHANES?
  • Contains all 22 of our non-invasive features

Key Design Decision

eGFR and creatinine are used only to construct the training labels (via the KDIGO grid). They are never used as model input features. The trained model works without them — enabling non-invasive deployment.

ML Architecture
Two-Stage Cascade Design
Separate models for at-risk detection and high-risk discrimination

22 Feature Input

All non-invasive patient features

↓

Stage 1 — Random Forest Gate

Binary: Low vs At-Risk · Threshold: 0.44 · Tuned for high sensitivity (catch all at-risk patients)

↓ if P(at-risk) ≥ 0.44

Stage 2 — Gradient Boosting Discriminator

Binary within at-risk pool: Moderate vs High · Threshold: 0.50

↓
LOW RISK
P(at-risk) < 0.44
MODERATE
P(high) < 0.50
HIGH
P(high) ≥ 0.50
Why Two Stages?
  • Stage 1 optimised for recall — never miss an at-risk patient
  • Stage 2 optimised for precision — accurately separate high from moderate
  • Minimises the most dangerous error: high→low misses
  • Handles severe class imbalance (low >> moderate > high)
+ Local Explanation

For every prediction: model-agnostic perturbation replaces each feature with a reference value and measures probability change. Top 6 factors with direction (raises/lowers risk) are surfaced to the user and passed to the LLM for personalisation.

Reliability Score

Each prediction receives a High / Moderate / Low reliability tag based on confidence margin, proximity to decision boundary, and missing feature count.

Key Safety Result

Only 2 High→Low misses on the entire test set. This is the clinically most dangerous error (patient needing follow-up told they're fine). The cascade design explicitly minimises this error type.

Moderate Class Note

Moderate recall (50.5%) reflects the inherent ambiguity of the moderate category — the boundary between moderate and high risk is noisy even with gold-standard eGFR+UACR. False moderate-as-low is far less dangerous than false high-as-low.

Personalisation Architecture

Three layers of personalisation ensure every patient's education is unique:

1. Patient Profile block — all 22 actual patient values in the prompt (age, SBP, HbA1c, diabetes flag, etc.)
2. Factor-aware RAG — different patients get different guideline chunks based on their top risk drivers
3. Per-section cues — explicit condition-derived instructions per output section (e.g. "For Food habits: address high blood sugar because HbA1c = 8.5%")

Why Rule-Based (Not LLM Judge)?

Deterministic, auditable, fast. A regex that blocks "you have CKD" will never fail on that pattern. Medical safety requires zero false-negatives on specific dangerous patterns — not probabilistic judgment.

Research Contribution
Novel Contributions
What Nephro-AI does that existing work does not

① Non-Invasive Feature Set

All existing ML CKD detection models use eGFR or creatinine as inputs. Nephro-AI is trained exclusively on routine, non-creatinine features — enabling community-level, pre-lab screening for the first time.

② KDIGO-Aligned Two-Stage Cascade

A Random Forest gate (tuned for recall) feeding a Gradient Boosting discriminator (tuned for precision) explicitly maps to KDIGO risk grid categories, with thresholds optimised to minimise High→Low misses.

③ Factor-Aware Personalised RAG

Rather than top-k by similarity (which collapses to the same chunks for all patients), the retriever builds a per-patient topic priority list from the ML explanation factors — guaranteeing different patients get different guideline chunks.

④ Safety-Scoped Knowledge Base

Chunks with individualised numeric targets (protein, potassium, sodium) are tagged "restricted" and served with a dietitian-referral override — not excluded. This preserves knowledge while preventing dangerous direct prescription.

⑤ Multi-Layer Validator with Measured 0% Unsafe Rate

A 7-layer deterministic rule engine (not probabilistic LLM judge) achieves a published 0% final unsafe rate on 30 adversarial profiles. Every decision is logged — fully auditable.

⑥ Full-Stack Patient + Admin System

A complete web application with a patient-facing view (simplified education) and a researcher-facing admin view (full audit trail: ML probabilities, retrieved chunks, validator decisions, frozen evaluation metrics).

Roadmap
Future Work
Extensions planned for the full research paper and clinical pilot
🎛️

QLoRA Fine-Tuning

Fine-tune Qwen3-4B on RAFT-generated training examples (question, correct guideline chunk, distractor). Expected to improve safety self-containment and output consistency beyond prompt engineering alone.

👨‍⚕️

Expert Clinical Evaluation

Structured review of LLM outputs by nephrologists and renal dietitians using a standardised rubric — clinical accuracy, safety, appropriateness. Required before any real-world deployment.

🌍

Population Generalisation

Validate on non-US datasets (South Asian, European, low-income country populations) where prevalence, comorbidity patterns, and reference ranges may differ from NHANES.

📈

Longitudinal Risk Tracking

Track serial screening results over time to detect deteriorating trends, trigger earlier follow-up, and measure whether patient education is changing behaviour — closing the feedback loop.

🌐

Multilingual Support

Bengali, Hindi, and Arabic patient education — targeting the populations most underserved by existing English-only kidney health materials. BGE-M3 already supports multilingual retrieval.

📦

Packaged Deployment

GGUF quantised model (Q4_K_M, ~3 GB) distributed with the app so any clinician can run the full system on a standard laptop — no cloud dependency, no patient data leaving the device.
